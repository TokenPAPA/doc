## 为什么 JSON 输出会颠覆常规的「最强模型」排序

大多数模型对比都是按聊天场景写的。结构化输出有三个特性会把排序打乱。

**1. schema 遵守度是一种技能，不是副作用。** 模型可能写得一手好散文，却照样发明字段名、漏掉必填键、把合法 JSON 包在 markdown 代码块里。你需要的是一次调用返回可解析、符合 schema 的 JSON 的概率——这更接近编程能力而非聊天能力，所以 `qwen3.7-plus`、`kimi-k2.7-code` 这类编程向模型经常比散文向模型表现更好。

**2. 输出 token 才是贵的 token。** 抽取调用发的是「提示词 + 文档」（输入），收的是 JSON（输出）。输出按 3-10 倍计价时，输入稍贵但输出便宜得多的模型，单次完成的成本反而更低。

**3. 重试是隐形账单。** 如果 2% 的调用返回非法 JSON 需要重试，强模型的实际成本就要把重试层算进去。合法率 98% 的便宜模型，总成本经常比合法率 99.5% 的强模型便宜 5-20 倍——这就是下面两段式管线的理由。

> **关键洞察**：结构化 JSON 输出这件事，**输入价格决定批量成本、schema 遵守度决定可靠性、重试决定账单上的惊喜**。按 TokenPAPA 费率，DeepSeek V4 Flash 输入比 GPT-5.6 Sol **便宜 96%**（$0.14 vs $13.50）——而抽取是输入密集负载，这个差距几乎原封不动地落到你月账单上。

## 哪些模型做结构化 JSON 真正可靠？

便宜只有在 JSON 能解析的前提下才有意义。四个能力决定你的 schema 能不能交给它：

| 能力 | 看什么 | 哪些模型站得住 |
|---|---|---|
| Schema 遵守度 | 每次调用是否命中声明的字段名与类型 | `qwen3.7-plus`、`gpt-5.4-mini`、`gpt-5.6-luna` 最稳 |
| 原生 JSON mode | 是否支持 `response_format: json_object` | 任意 OpenAI 兼容端点，含 TokenPAPA 的 `https://tokenpapa.ai/v1` |
| 编程能力 | 看代码基准而不是聊天基准 | DeepSeek V4 Flash 在 Terminal Bench 2.1 得分 **82.7**，超过贵 50 倍的模型 |
| 长上下文 | 窗口能否放下整份文档 | 128K 覆盖大多数场景；`kimi-k3`（256K）与 `gpt-5.6-luna`（1M）留给长文档 |

实践原则：**让校验器选模型，而不是让排行榜选模型**。拿真实 schema 在 2-3 个候选上各跑一批，量一下「一次合法率」和修复成本再定。在 TokenPAPA 上这个实验一个下午就能做完——所有候选共用一个 Key，只差一个 `model=` 字符串。多模型路由与降级的机制，和 [如何用 60 个模型日路由 100 万次 API 调用](https://doc.tokenpapa.ai/zh/docs/blog/routing-1m-api-calls-daily-60-models) 里讲的是同一套模式。

## 怎么用一个 Key 让任意模型强制输出合法 JSON？

不需要单独的「JSON 端点」。OpenAI 兼容 API 支持 `response_format: {"type": "json_object"}` 参数，TokenPAPA 上所有模型通过同一个 `base_url` 都接受它。两个细节决定成败：schema 写在提示词里，`max_tokens` 必须显式设置——被截断的 JSON 就是非法 JSON。

```python
from openai import OpenAI

client = OpenAI(
    api_key="your-tokenpapa-key",
    base_url="https://tokenpapa.ai/v1"
)

SCHEMA = """把下面邮件内容抽取为客户记录 JSON，字段必须完全一致：
{"company": 字符串, "contact_email": 字符串, "plan": "free"|"pro"|"enterprise",
 "annual_revenue_usd": 数字, "signup_date": "YYYY-MM-DD"}
只输出 JSON 对象本身，不要包 markdown 代码块。"""

response = client.chat.completions.create(
    model="qwen3.7-plus",              # 可换 deepseek-v4-flash 或 gpt-5.6-luna
    messages=[
        {"role": "system", "content": SCHEMA},
        {"role": "user", "content": email_text},
    ],
    response_format={"type": "json_object"},
    max_tokens=400,                    # 显式限制昂贵的输出 token
)

import json
record = json.loads(response.choices[0].message.content)
```

同样的调用形状：`deepseek-v4-flash` 当预算抽取器，`gpt-5.6-luna` 处理长文档或嵌套 schema。想走 OpenAI 风格的声明式 schema，就用 `response_format={"type": "json_schema", "json_schema": {...}}`，平台原样透传，详解见 [OpenAI 兼容性指南](https://doc.tokenpapa.ai/zh/docs/blog/openai-compatibility-guide)。

两个习惯能消除绝大多数非法 JSON：第一，**提示词保持稳定**——schema 字符串固定不变，让服务端缓存把重复前缀打折（这正是 agent 循环降本的同款技巧，见 [2026 年跑 AI Agent 最便宜的大模型 API](https://doc.tokenpapa.ai/zh/docs/blog/cheap-llm-api-for-ai-agents)）；第二，**每个调用都套一层校验重试**——`json.loads` 解析失败就把校验器报错拼回去重发一次。

## 用一个模型还是两段式管线？

单模型抽取在「账单」或「失败率」开始烦人之前都没问题。两段式管线不需要新基建：

**第一段 —— 批量抽取（每份文档）。** `deepseek-v4-flash` 以约 $0.41 / 1000 次调用承接海量工作。因为 schema 字符串稳定且输入密集，DeepSeek 的自动上下文缓存对重复输入约打 **9 折**（详见 [DeepSeek 缓存命中优化](https://doc.tokenpapa.ai/zh/docs/blog/deepseek-cache-hit-optimization)）。

**第二段 —— 修复与高风险重试。** 校验器拒绝某条记录，或文档是合同而不是发票时，把这一次重试升级到 `qwen3.7-plus`（schema 遵守度）或 `gpt-5.6-luna`（长上下文 + 结构化输出）。升级只是改一个 `model=` 字符串——和审查管线里「第三个模型做裁决」是同一套思路（[2026 年代码审查该用哪个大模型](https://doc.tokenpapa.ai/zh/docs/blog/best-llm-for-code-review-2026)）。

每一段共用一个 Key、一个 base_url，这条管线本质上是一张 model 字符串字典，而不是一堆厂商集成。
