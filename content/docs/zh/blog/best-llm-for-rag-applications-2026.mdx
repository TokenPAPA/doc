# 2026 年做 RAG 该用哪个大模型？按「一次问答成本」选型

问十个工程师「RAG 用哪个模型」，会得到十个基于榜单的答案。但检索增强生成不是榜单型负载，**它是账单型负载**：每次调用都要塞进五段检索结果、一套引用规则和一个问题，只吐回一小段话。典型是 **8000 token 输入、500 token 输出**——输入占 94%。所以「哪个最好」的关键不在于谁推理更强，而在于谁把重复上下文卖得最便宜、以及它的缓存到底能不能命中。

下面按这个工作量实测 17 个模型在 TokenPAPA 上的价格，看开启缓存后排名怎么变，并给出一套可以拿自己文档跑的忠实度测试。

> **一句话结论**：对大多数团队，最好的 RAG 模型是**能通过你引用校验的最便宜的那个**，因为一次 RAG 调用里 94% 的 token 是重复上下文。按 TokenPAPA 实时价格（2026-11-19 读取），缓存命中 75% 时，Mimo V2.6 Flash 每 1000 次带引用回答约 **0.49 美元**，DeepSeek V4 Flash 约 **1.26 美元**，Claude Sonnet 5.5 与 GPT-6.1 Sol 约 **8.97 美元**，Claude Fable 5.1 约 **44.54 美元**。先用便宜档跑，只升级校验失败的问答。

## 为什么 RAG 的账单和聊天完全不是一个形状

聊天是一问一答、输入输出差不多长。RAG 是故意做成「读得多、写得少」的——这正是检索的意义。

| 提示词组成 | token 数 | 是否每次重复 |
|---|---:|:---:|
| 系统提示 + 引用规则（只依据上下文、标注 chunk id、无依据则拒答） | ~1000 | 是 |
| 检索到的文档片段（5 段 × 约 1000 token） | ~5000 | 是（多轮或同一文档集） |
| 新检索结果 + 用户问题 + 少量历史 | ~2000 | 否 |
| **输入合计** | **~8000** | |
| **输出（答案 + 引用标记）** | **~500** | |

也就是 **94.1% 输入、5.9% 输出**。三个直接结论：

1. **输出倍率没那么可怕**，因为它只作用在 6% 的 token 上；
2. **输入单价和缓存倍率决定一切**——8000 token 里有 6000 是逐字节相同的，正好是 prompt 缓存设计的场景；
3. **输出预算留太大纯属浪费**——把 `max_tokens` 留在 2000，你就是在为模型根本不需要写的 token 付钱。

> **关键结论**：RAG 里模型每写 1 个 token 要读约 16 个 token。任何从「输出价格」开始的选型，优化的都是那 6%。

## 如果你的上下文根本缓存不上怎么办

有些检索器天生缓存不命中：每次请求都重新排序、把时间戳或用户 id 塞进上下文、或者每次查的文档集都不同。这时你只能看「冷」那一列。

- **便宜输入价的模型直接胜出**：Doubao Seed 2.0 Lite（1.03）、GLM-5.3-Flash（1.17）、Qwen 3.8 Flash（1.21）、Mimo V2.6 Flash（1.40）都比 DeepSeek V4 Flash（3.00）便宜一半以上。
- **砍提示词比换模型更有效**：把检索上下文从 5000 砍到 3200 token（5 段小片段代替 5 段大片段），全模型账单同时降 22%，只要重排器不太差，质量基本无感。

各家的缓存计费细节不同，做成本模型前先确认你的路由支持什么。TokenPAPA 上每个模型的缓存价都列在[定价页](https://tokenpapa.ai/pricing)，缓存命中的计费机制可参考[大模型 token 计费详解](https://doc.tokenpapa.ai/zh/docs/blog/llm-token-pricing-explained)。

## 便宜的模型会答得更差吗

有时候会，但失败方式很具体，不是笼统的「笨」。带依据回答比推理简单——答案通常就摆在上下文里——所以 0.003 美元和 0.46 美元缓存价的差距，集中体现在四个地方：

| 失败模式 | 表现 | 便宜模型为什么栽 |
|---|---|---|
| 抛弃上下文 | 用参数记忆回答，无视检索片段 | 长上下文指令遵循弱 |
| 引用漂移 | 答案对，chunk id 指错 | span 定位能力差 |
| 无依据自信 | 上下文里没有也照样编数字 | 拒答校准差 |
| 长上下文衰减 | 超过 5-6 段后质量下滑 | 注意力稀释 |

这四项都不会出现在通用榜单上，但都很容易测。准备 100-200 条真实问题，每条标注正确答案和对应的 chunk id，然后分开打四个分：答案正确性、引用精确度、**不可答问题上的拒答率**（另准备 20 条语料里没有答案的问题）、以及编造率。全部用 `temperature: 0` 跑同一套题。

实测经验是：最便宜那档在单跳问题上正确性和引用都不差，栽的是多跳综合和拒答——这正是下面分流方案存在的理由。需要更严谨的评测方法，可以借用 [Text-to-SQL 评测指南](https://doc.tokenpapa.ai/zh/docs/blog/best-llm-for-sql-generation-2026)里的执行准确率思路：比对标准答案，而不是凭感觉。

## 提示词怎么写，缓存才真的命中

缓存是前缀匹配。任何在提示词前部变化的内容都会让后面全部失效，所以顺序不是文风问题，而是机制本身。

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["TOKENPAPA_API_KEY"],
    base_url="https://tokenpapa.ai/v1",
)

# 1. 静态块：每次完全一致 → 可缓存前缀
SYSTEM = """只依据给定上下文回答。
规则：
- 每个结论后用方括号标注 chunk id。
- 上下文里没有答案时，只回复 NOT_IN_CONTEXT。
- 不使用外部知识，不编造数字。"""

def answer(question: str, chunks: list[dict]) -> str:
    # 2. 半静态块：检索上下文，顺序稳定，不塞时间戳
    context = "\n\n".join(f"[{c['id']}] {c['text']}" for c in chunks)
    resp = client.chat.completions.create(
        model="deepseek-v4-flash",       # 换成 qwen3.8-flash 即可，其他不用改
        temperature=0,
        max_tokens=600,                  # 带引用的回答很短，不要为多余输出付钱
        messages=[
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": f"CONTEXT:\n{context}\n\nQUESTION: {question}"},
        ],
    )
    return resp.choices[0].message.content
```

三条规则决定你是 75% 命中还是 0%：

- **系统提示里绝不放假时间戳、请求 id、用户名**——前缀每次都变，你就永远按全价付费；
- **chunk 顺序必须确定**——按分数排序，不要用字典遍历顺序，否则同样的问题前缀也不一样；
- **`max_tokens` 必须设上限**——输出有 3-8 倍倍率，600 对带引用的回答不是质量风险，是成本控制。

完整链路（切片、重排、成本模型）可以看[DeepSeek RAG 成本指南](https://doc.tokenpapa.ai/zh/docs/blog/deepseek-rag-cost-guide)。

## 常见问题

### 2026 年做 RAG 该用哪个大模型？

没有唯一答案，因为 RAG 一次调用里 94% 的 token 是输入。按 8000 token 输入、500 token 输出计算，缓存命中率 75% 时，Mimo V2.6 Flash 每 1000 次回答约 0.49 美元，Qwen 3.8 Flash 约 0.58 美元，DeepSeek V4 Flash 约 1.26 美元，Claude Sonnet 5.5 与 GPT-6.1 Sol 同为 8.97 美元。合理做法是先用便宜档跑，只把引用校验失败的问答升级到强模型。

### 为什么 RAG 场景里 prompt 缓存比单价更重要？

因为检索到的文档片段和系统提示每轮都要重发，而且大部分完全相同。在 8000 token 的 RAG 提示词里，可缓存部分约占 75%，而缓存输入价从 Mimo V2.6 Flash 的 0.003 美元每百万 token 到 GPT-5.6 Sol 的 0.46 美元，相差 150 倍。忽略缓存倍率，两个输出倍率相同的模型实测成本可能差 4 倍。

### 怎么验证便宜的模型做 RAG 够不够用？

准备 100 到 200 条真实问题，每条标注正确答案和包含答案的 chunk id，然后分开打四个分：答案正确性、引用精确度、上下文缺失时的拒答率、以及是否编造了上下文里没有的事实。后两项是用户最容易察觉的失败点，而它们不会出现在通用榜单上。

### 换 RAG 模型要重写整条链路吗？

不需要。TokenPAPA 提供 OpenAI 兼容端点 `https://tokenpapa.ai/v1`，一个 Key 可调用 60 个以上模型条目，从 `deepseek-v4-flash` 换到 `qwen3.8-flash` 或 `claude-sonnet-5-5` 只改一行 model 名，检索器、提示词模板和引用解析都不用动。

### RAG 的输出预留 2000 token 是不是浪费？

是，除非你设了上限。带引用的回答通常 400 到 600 token 就够，而输出 token 在多数模型上是 3 到 8 倍倍率。把 `max_tokens` 设成 600 是 RAG 链路里最快见效的成本优化，同时让延迟变得可预测。
