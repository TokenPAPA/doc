# 2026 年翻译用哪个大模型 API 最便宜?19 个模型百万字成本对比

翻译是最古老的 LLM 场景,也是最容易在价格上判断失误的场景。团队通常先比较输入价格、挑一个最低的,然后发现真正决定账单的完全是另一件事:输出那一侧。

这篇文章按一份真实的本地化工作量来定价——**一百万个英文源词译成目标语言**——用 TokenPAPA 在 2026-11-21 读取的实时单价,横向对比 19 个模型。重点讲三件事:为什么输出 token 在翻译里是账单主角,为什么关于提示词缓存的常规建议在这里几乎无效,以及怎么验证一个每百万词 0.70 美元的模型是否真的能上线。

> **一句话结论**:做文档翻译时,应该按**输出价格**排序,而不是按输入价格,因为输出 token 只占工作量 46%,却要付 71%-98% 的账单。按 TokenPAPA 2026-11-21 的实时价格,每百万源词成本约为:Mimo V2.6 Flash **0.70 美元**、Claude Haiku 5.5 **0.82 美元**、GLM-5.3-Flash **0.85 美元**、Qwen 3.8 Flash **0.97 美元**、DeepSeek V4.1 Flash **2.32 美元**、Claude Sonnet 5.5 与 GPT-6.1 Sol **17.36 美元**、GPT-5.6 Sol **65.70 美元**。最便宜和最贵相差 **94 倍**,译的却是同一批文字。

---

## 为什么翻译的计费结构与聊天、RAG 完全不同?

聊天是「读一句、写一段」。RAG 是「读 8000 token 上下文、写 500 token 答案」。翻译的形状与 RAG 恰好相反:**每次都在读全新的原文,并写出长度相当的全新译文。**

本文定价的工作量如下,按一百万源词计算:

| 组成部分 | token 数 | 能否跨请求复用 |
|---|---:|---:|
| 原文(英文约 1.3 token/词) | 1,300,000 | **不能**,每次都是新文本 |
| 系统提示词 + 术语表 + 风格规则(每 1000 词分块 600 token,共 1000 块) | 600,000 | 可缓存 |
| **输入合计** | **1,900,000** | |
| **输出**(译文,约 1.6 token/源词) | **1,600,000** | |

也就是 **54.3% 输入、45.7% 输出**,几乎是五五开。对比本月早先那篇 RAG 文章里的 94.1% 输入占比,就能明白为什么两篇文章给出的建议截然不同。

再乘上价格乘数。平台上所有模型的输出单价都高于输入单价,乘数从 **1 倍到 50 倍**不等。在一个 46% 是输出的工作量上,这个乘数不是细节,它就是账单本身。

> **核心洞察**:RAG 里模型每写 1 个 token 要读 16 个 token;翻译里它写出的 token 超过读入的一半,而且每个都贵 2 到 50 倍。同样是 LLM 调用,优化目标完全不同。

## 为什么输出乘数比标价更重要?

因为翻译写出的量和读入的量相当。把乘数并排摆出来,排名就不再意外:

| 模型 | 输出乘数 | 输出占账单 |
|---|---:|---:|
| Gemini 3.5 Flash | **1.0×** | 54% |
| Mimo V2.6 Flash | **2.0×** | 71% |
| Qwen 3.7 Max | 2.7× | 74% |
| Hy4 | 2.8× | 77% |
| GLM-5.3-Flash | 3.5× | 79% |
| DeepSeek V4.1 Flash | 4.0× | 83% |
| Qwen 3.8 Flash | 4.2× | 83% |
| Claude Sonnet 5.5 / GPT-6.1 Sol | 5.0× | 86% |
| Claude Opus 5.5 | 5.0× | 86% |
| GPT-5.6 Sol | 8.0× | 90% |
| Claude Haiku 5.5 | **50.0×** | 98% |

两条实用规则:

- **低输入价救不了高输出乘数。** Haiku 5.5 是最典型的例子:输入几乎免费,98% 的成本仍然是输出。如果月翻译量在两千万词级别,这个差别是几百美元。
- **两个模型输出价接近时,再用输入价做仲裁。** Mimo V2.6 Flash(输出 0.31 美元)和 Claude Haiku 5.5(输出 0.50 美元)在输出侧差 61%,所以尽管 Mimo 输入价贵 16 倍,总价仍然更低。

## 术语表缓存和分块,真的能省钱吗?

不能,而且原因是结构性的,不是某家平台的实现问题。RAG 里每个提示词有 75% 是逐字节相同的检索上下文——缓存就是为这种形状发明的。翻译的原文按定义每次都不一样,唯一可复用的前缀只有系统提示词和术语表,只有几百 token。

下面是同一份百万词工作量在 DeepSeek V4.1 Flash 上,随分块大小变化的结果(术语表按缓存价计费):

| 每次请求词数 | 每百万词计费的术语表 token | 每百万词总成本 |
|---:|---:|---:|
| 500 | 1.20M | $2.32 |
| 1,000 | 0.60M | $2.32 |
| 2,000 | 0.30M | $2.31 |
| 4,000 | 0.15M | $2.31 |
| 8,000 | 0.08M | $2.31 |

术语表开销扩大八倍,账单只动了**每百万词一分钱**。原因是缓存价约等于该模型输入价的 3%,而术语表在「绝大多数是新原文和新译文」的工作量里只占很小一块。

> **关键结论**:提示词缓存在 RAG、Agent 循环和多轮对话里值得专门优化,在文档翻译里基本是四舍五入级别的误差。把这份工程时间花在**分句质量、术语表强制约束和输出上限**上,回报高得多。

缓存真正有用的翻译场景是另一种:实时聊天翻译每小时把同一段系统提示词重发几千次,或者翻译记忆库反复回放相同的语段。缓存命中跟着**重复的前缀**走,而不是跟着重复的意图走。

## 每百万 token 75 美元的专用翻译模型,值吗?

价格表里最有意思的是最后一行。平台目录中的 **Hy-MT2 Pro** 是专用机器翻译模型,不是通用对话模型,标价**每百万输入 75 美元、每百万输出 300 美元**。按上面的工作量折算,就是**每百万源词 622.50 美元**:约为 Mimo V2.6 Flash 的 **890 倍**,也是 GPT-5.6 Sol 的 **36 倍**。

这个价格只有一个成立条件:它能替掉人工后编辑。把账算实在,盈亏平衡点很好说。相对中端通用模型,它每百万词贵约 605 美元;按 30 美元/小时的后编辑成本,等于**每百万词 20 小时人工**,也就是**每千词 1.2 分钟**。如果专用模型帮你省下的修改时间不到每千词一分多钟,那它就是更贵的选择——尽管它听起来才是「为翻译而生」的那个。

专用 MT 模型值得试的场景很具体:大批量、合规或品牌敏感、且本来就有专业审校在流程里,唯一的问题只是每页要改几处。内部文档、客服话术、商品短描述这类「谁提需求谁自己看一眼」的内容,基本用不上它。

> **关于目录可用性的提醒**:目录标价和实际可调用是两件事。决定围绕某个专用模型搭流水线之前,先用你自己的 key 发一次真实请求,确认路由真的通了——模型可能挂在目录里但上游通道是空的。任何你还没调用过的新条目,都按这个方式验一遍。

## 怎么判断便宜的模型够不够用?

量四件事,而且要用你自己的文本量,不要看榜单。通用基准上的翻译分数,几乎说明不了模型会不会遵守你的产品术语、会不会保留你的 Markdown。

| 检查项 | 抓什么问题 | 怎么做 |
|---|---|---|
| **术语命中率** | 产品名、法律术语、品牌口吻漂移 | 给一份 50 词术语表,数输出里的精确匹配,目标 >98% |
| **占位符完整性** | 翻译后模板被改坏 | 原文里放变量、HTML 标签和 Markdown,解析输出并断言每个标记都在 |
| **参考相似度** | 静默漏译、丢句 | 用 200-500 条人工译文做参考,算 chrF 或 COMET |
| **每千词缺陷数** | 人一眼能看出的所有问题 | 母语审校盲评,数修改处,不数主观感受 |

每个候选模型都用低温度、同一套提示词跑,并记录**每条被接受语段的成本**,而不是每 token 价格。每百万词 0.70 美元但要 15% 返工的模型,并不比 0.97 美元只要 5% 返工的模型便宜——把两个数字相除,你得到的是决策而不是偏好。

占位符完整性值得单列一步,因为它是唯一会直接把线上搞挂的失败。测试是机械的:

```text
原文:  Hello {first_name}, your order #{order_id} ships on {date}.
       See **{policy_link}** for details.
要求:  每个 {variable} 和每个 ** 标记都恰好出现一次,
       变量名不被翻译,Markdown 定界符不被重排
```

把 `{first_name}` 翻成本地化变量名的模型,句子再漂亮也是没通过。把这一步做成硬性闸门,并保留一个确定性回退:解析失败就把整段回退成原文。

## 什么场景选什么模型?

| 你的情况 | 选 | 理由 |
|---|---|---|
| 大批量文档本地化、成本敏感 | **Mimo V2.6 Flash**($0.70) | 全表最低,输出乘数 2 倍 |
| 语段极短、输入价主导 | **Claude Haiku 5.5**($0.82) | 输入 0.01 美元,冷启动最便宜 |
| 混合负载、想要一个默认值 | **GLM-5.3-Flash**($0.85)或 **Qwen 3.8 Flash**($0.97) | 输出价与多语种覆盖较均衡 |
| 中英互译为主 | **Qwen 3.8 Flash**、**Qwen 3.7 Plus** 或 **Hy4** | 中英平行语料训练充分 |
| 超长文档、输出占绝对主导 | **Gemini 3.5 Flash**($3.59) | 1 倍输出乘数,锁住输出侧敞口 |
| 法务、医疗、品牌文案 | **Claude Sonnet 5.5** 或 **GPT-6.1 Sol**($17.36) | 指令与术语遵守最稳 |
| 确实需要专用 MT 模型 | **Hy-MT2 Pro**($622.50) | 只有能量化省下的后编辑时间才成立 |

多数团队的实际做法是两级流水线:便宜档吃下全部内容,一个校验环节抓术语漏译和占位符失败,只有失败的语段升级到更强的模型。因为一个 OpenAI 兼容 key 就能调平台上所有模型,这个升级只是改一个模型字符串,不是再接一套集成。同样的路由思路也是 [Agent 负载省钱](https://doc.tokenpapa.ai/zh/docs/blog/best-llm-for-rag-applications-2026)的核心,而更细的 token 计费机制在[价格速查表](https://doc.tokenpapa.ai/zh/docs/blog/llm-api-pricing-cheat-sheet-2026)里。

## 代码长什么样?

整套优化就在一段代码里:可缓存的术语表前缀、占位符闸门、受限的输出预算,以及决定是否升级的校验。

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["TOKENPAPA_API_KEY"],
    base_url="https://tokenpapa.ai/v1",
)

GLOSSARY = """Translate English into Simplified Chinese.
Keep these terms in English exactly as written: TokenPAPA, API key, base_url, endpoint.
Preserve every {variable}, HTML tag and Markdown marker exactly.
Output only the translation, with no commentary."""

def translate(segment: str, model: str = "deepseek-v4.1-flash") -> str:
    resp = client.chat.completions.create(
        model=model,
        temperature=0.2,
        max_tokens=int(len(segment.split()) * 4),  # 输出上限,别为空白付钱
        messages=[
            {"role": "system", "content": GLOSSARY},   # 可缓存前缀,放最前
            {"role": "user", "content": segment},
        ],
    )
    return resp.choices[0].message.content

def placeholders(text: str) -> set[str]:
    import re
    return set(re.findall(r"\{[a-z_]+\}", text))

def translate_safe(segment: str) -> str:
    out = translate(segment)
    if placeholders(segment) != placeholders(out):
        out = translate(segment, model="claude-sonnet-5-5")  # 只升级一次
    return out
```

比选模型更重要的有两个细节。`max_tokens` 要按语段长度推算,而不是留默认值——中文/日文在某些语言对上 token 数比英文源更长、在另一些上更短,给一个宽裕的默认值纯属浪费。术语表必须放在 **system** 消息里、在原文之前,否则根本不可能命中缓存;放到原文后面等于每次都保证 miss。

如果要更完整的服务——队列、批处理、术语库——[DeepSeek 翻译 API 实战指南](https://doc.tokenpapa.ai/zh/docs/blog/deepseek-translation-api-guide)用同一套价格模型给出了 FastAPI 版本的封装。

## 常见问题

### 2026 年翻译用哪个大模型 API 最便宜?

按 TokenPAPA 2026-11-21 的实时价格,文档翻译最便宜的是 Mimo V2.6 Flash,每百万源词约 0.70 美元,其次是 Claude Haiku 5.5 的 0.82 美元、GLM-5.3-Flash 的 0.85 美元、Qwen 3.8 Flash 的 0.97 美元。同样的文本用 Claude Sonnet 5.5 或 GPT-6.1 Sol 是 17.36 美元,用 GPT-5.6 Sol 约 65.70 美元,相差 94 倍。

### 为什么翻译的计费结构和聊天、RAG 不一样?

因为翻译写出的 token 几乎和读入的一样多。一百万源词对应约 130 万输入 token 的新文本、60 万 token 的可复用术语表、160 万输出 token;输出只占 token 总量的 46%,却占账单的 71%-98%,原因是输出价格带 2 到 50 倍乘数。按输入价选模型,优化的是账单里较小的那一半。

### 提示词缓存能降低翻译成本吗?

几乎不能,这正是它和 RAG 的结构性差别。翻译的原文每次都是新的,唯一可缓存的前缀只有系统提示词和术语表,大约每次 600 token。把分块从 4000 词降到 500 词,术语表开销翻四倍,但在 DeepSeek V4.1 Flash 上总账单只从每百万词 2.31 美元变成 2.32 美元,变化不到 1%。

### 专用机器翻译模型比通用大模型便宜吗?

不,按 token 算贵得多。目录里 Hy-MT2 Pro 标价每百万输入 75 美元、每百万输出 300 美元,折算每百万源词约 622.50 美元,是 Mimo V2.6 Flash 的 0.70 美元的约 890 倍。只有当它每百万词能省下约 20 小时人工后编辑时才划算,所以先量缺陷率再谈省钱。

### 怎么判断便宜的翻译模型够不够用?

在 200 到 500 条真实语段上做四项可量化的检查:对照术语表的术语命中率、变量与 Markdown 标记的完整性、对照参考译文的 chrF 或 COMET 分数、母语审校的每千词缺陷数。按「每条被接受语段的成本」比较,而不是每 token 价格,因为返工才是让便宜模型变贵的真正原因。
