# Which LLM API Is Cheapest for Translation in 2026?

Translation is the oldest LLM workload there is, and it is the one where price intuition fails most often. Teams compare input prices, pick the model with the lowest number, and then discover that their bill is decided by something else entirely: the output side.

This guide prices a realistic localisation job — one million source words, English into a target language — across 19 models on TokenPAPA, using live per-token rates read on 2026-11-21. It explains why output tokens dominate a translation invoice when they dominate nothing in a RAG pipeline, why the usual advice about prompt caching does almost nothing here, and how to test whether a $0.70-per-million-words model is actually good enough to ship.

> **Best LLM for translation, in one paragraph**: for document translation, rank models by output price, not input price, because output tokens are 46% of the workload and 71-98% of the bill. On TokenPAPA's live rates (2026-11-21), Mimo V2.6 Flash costs about **$0.70 per million source words**, Claude Haiku 5.5 about **$0.82**, GLM-5.3-Flash about **$0.85**, Qwen 3.8 Flash about **$0.97**, DeepSeek V4.1 Flash about **$2.32**, Claude Sonnet 5.5 and GPT-6.1 Sol about **$17.36**, and GPT-5.6 Sol about **$65.70**. The spread between the cheapest and most expensive general model is **94×** for identical text.

## Why does translation billing look nothing like chat or RAG billing?

A chatbot call reads a short question and writes a similar-length answer. A RAG call reads 8,000 tokens of retrieved context and writes 500. Translation is the opposite shape from RAG: it **reads new text and writes new text of comparable length**, every single time.

Here is the workload this article prices, for one million source words:

| Component | Tokens | Reusable across calls? |
|---|---:|---:|
| Source text (1.3 tokens per English word) | 1,300,000 | **No** — always new |
| System prompt + glossary + style rules (600 tokens per 1,000-word chunk, 1,000 chunks) | 600,000 | Yes, if cached |
| **Total input** | **1.9M** | |
| **Output** (target text, 1.6 tokens per source word) | **1,600,000** | |

That is **54.3% input and 45.7% output** — a near-even split. Compare it with the RAG workload we priced earlier this month at 94.1% input, and the reason the advice differs becomes obvious.

Then apply the price multiplier. Every model on the platform charges more for output than for input, and the multiplier ranges from **1× to 50×**. On a workload that is 46% output, that multiplier is not a detail — it is the invoice.

> **Key insight**: in RAG the model reads about 16 tokens for every token it writes. In translation it writes more than half the tokens it reads, and each of those tokens costs 2 to 50 times more. Two workloads, two completely different optimisation targets.

## Does glossary caching or chunking actually save money?

No, and the reason is structural rather than a quirk of any provider. In a RAG pipeline 75% of every prompt is byte-identical retrieved context — caching was invented for that shape. In translation the source text is different on every call by definition. The only reusable prefix is your system prompt and glossary, and that is a few hundred tokens.

Here is the effect of chunk size on the same one-million-word job, on DeepSeek V4.1 Flash, with the glossary billed at its cached price:

| Words per request | Glossary tokens billed per 1M words | Total cost per 1M words |
|---:|---:|---:|
| 500 | 1.20M | $2.32 |
| 1,000 | 0.60M | $2.32 |
| 2,000 | 0.30M | $2.31 |
| 4,000 | 0.15M | $2.31 |
| 8,000 | 0.08M | $2.31 |

An eight-fold increase in glossary overhead moves the bill by **one cent per million words**. The cached rate is roughly 3% of the input rate on this model, and the glossary is a small fraction of a workload whose bulk is fresh source and output text.

> **Key takeaway**: prompt caching is worth engineering for in RAG, in agent loops and in multi-turn chat. For document translation it is a rounding error. Spend that engineering time on segmentation quality, glossary enforcement and output caps instead.

Where caching *does* matter in translation is a different workload: a live chat translator resending the same system prompt thousands of times per hour, or a translation memory that replays the same source segments. Cache hits follow repeated prefixes, not repeated intentions.

## Is a dedicated machine translation model worth $75 per million tokens?

The most interesting line in the price table is the last one. The TokenPAPA catalog lists **Hy-MT2 Pro** — a translation-specialised model, not a general chat model — at **$75 per million input and $300 per million output tokens**. On the workload above, that is **$622.50 per million source words**: about **890× Mimo V2.6 Flash** and **36× GPT-5.6 Sol**.

That price only makes sense under one condition: it removes human post-editing. Do the arithmetic honestly and the break-even is easy to state. The gap against a mid-tier general model is roughly $605 per million words. At a post-editing rate of $30 per hour, that is **about 20 hours of editing per million words**, or **1.2 minutes per 1,000 words**. If the specialised model saves you less than a minute and a quarter of fixes per thousand words, it is the more expensive choice despite sounding like the purpose-built one.

A dedicated MT model is worth testing when you are producing regulated or brand-sensitive text at volume, where a professional reviewer is already in the loop and the only question is how many corrections they make per page. It is almost never worth it for internal content, support macros or catalogue copy, where output is checked by the person who asked for it.

> **Note on catalogue availability**: list price in the catalogue and callability are two different facts. Before you design a pipeline around a specialised model, send one real request through your own key and confirm the route answers — a model can be listed and still have no live upstream channel. Check the same way for any new entry you have not called yet.

## How do you know a cheap model is good enough?

You measure four things, and you measure them on your own text rather than on a leaderboard. Translation quality on a general benchmark says very little about whether a model respects your product glossary or preserves your Markdown.

| Test | What it catches | How to run it |
|---|---|---|
| **Terminology hit rate** | Product names, legal terms, brand voice drift | Ship a 50-term glossary, count exact matches in output; target >98% |
| **Placeholder integrity** | Broken templates after translation | Include variables, HTML tags and Markdown in the source; parse the output and assert every token survived |
| **Reference similarity** | Silent omissions, dropped sentences | Score against 200-500 human-translated segments with chrF or COMET |
| **Defect rate per 1,000 words** | Everything a human notices | Blind spot check by a native reviewer, count corrections, not opinions |

Run every candidate at a low temperature with the same prompt, and record **cost per accepted segment** rather than cost per token. A model at $0.70 that needs 15% rework is not cheaper than one at $0.97 that needs 5% — take the ratio of the two numbers and you have a decision, not a preference.

Placeholder integrity deserves its own step because it is the failure that breaks production. The test is mechanical:

```text
source:  Hello {first_name}, your order #{order_id} ships on {date}.
         See **{policy_link}** for details.
expect:  every {variable} and every ** marker present exactly once,
         no translated variable names, no reordered markdown fences
```

A model that translates `{first_name}` into a localised identifier has failed the test no matter how elegant the sentence reads. Treat this as a hard gate, and keep a deterministic fallback that reverts the whole segment to the source when the parse fails.

## What does the code look like?

The whole optimisation in one snippet: a cached glossary prefix, a placeholder guard, a capped output budget, and a validation step that decides whether to escalate.

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["TOKENPAPA_API_KEY"],
    base_url="https://tokenpapa.ai/v1",
)

GLOSSARY = """Translate English into Simplified Chinese.
Keep these terms in English exactly as written: TokenPAPA, API key, base_url, endpoint.
Preserve every {variable}, HTML tag and Markdown marker exactly.
Output only the translation, with no commentary."""

def translate(segment: str, model: str = "deepseek-v4.1-flash") -> str:
    resp = client.chat.completions.create(
        model=model,
        temperature=0.2,
        max_tokens=int(len(segment.split()) * 4),  # cap output, do not pay for padding
        messages=[
            {"role": "system", "content": GLOSSARY},   # cacheable prefix, first
            {"role": "user", "content": segment},
        ],
    )
    return resp.choices[0].message.content

def placeholders(text: str) -> set[str]:
    import re
    return set(re.findall(r"\{[a-z_]+\}", text))

def translate_safe(segment: str) -> str:
    out = translate(segment)
    if placeholders(segment) != placeholders(out):
        out = translate(segment, model="claude-sonnet-5-5")  # escalate once
    return out
```

Two details matter more than the model choice. `max_tokens` is derived from the segment length instead of being left at a default — CJK output runs longer in tokens than the English source in some pairs and shorter in others, so a generous default is pure waste. And the glossary sits in the **system** message, ahead of the source text, so it can be cached at all; putting it after the source text guarantees a cache miss on every call.

For a fuller service — queueing, batching and a glossary store — the [DeepSeek translation API guide](https://doc.tokenpapa.ai/en/docs/blog/deepseek-translation-api-guide) walks through the same pricing model with a FastAPI wrapper.
