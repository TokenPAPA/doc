# Which LLM Is Best for SQL Generation in 2026?

Every "cheapest model" list you have read was built for chatbots, where one message in roughly equals one message out. **Text-to-SQL is the opposite shape**: you paste a schema, a handful of few-shot examples and some retrieved rows on every single call, and the answer is one short query. In a normal setup the model reads about 5,500 tokens and writes about 160. That single ratio — not the headline price — decides which model is actually best for SQL generation, and it is why teams that pick a model by output price end up overpaying by an order of magnitude.

This guide measures the real thing. It prices 13 models on TokenPAPA for a realistic text-to-SQL workload, shows why prompt caching changes the ranking, and gives you an accuracy test you can run on your own schema instead of trusting a leaderboard.

> **Best LLM for SQL generation, in one paragraph**: for most teams the best model is not the strongest one, it is the cheapest one that clears your accuracy bar, because 97% of the tokens in a text-to-SQL prompt are repeated context. On TokenPAPA's live prices, DeepSeek V4 Flash costs about **$4.09 per 10,000 queries** with a 95% cache hit on the schema prefix, Qwen 3.8 Flash about **$2.21**, and Claude Sonnet 5.5 or GPT-6.1 Sol about **$30.24** for the same workload. Run a cheap tier first, escalate only the queries that fail validation.

## Why text-to-SQL breaks normal model selection

A chat completion is balanced: a 400-token question and a 400-token answer. A text-to-SQL call is lopsided, and the lopsidedness is structural, not incidental.

| Component of the prompt | Tokens | Repeat on every call? |
|---|---:|:---:|
| Schema DDL (about 30 tables, columns, types, comments) | ~4,200 | Yes |
| Few-shot exemplars (4 question → SQL pairs) | ~900 | Yes |
| Retrieved sample rows / value hints | ~340 | Partly |
| User question | ~60 | No |
| **Total input** | **~5,500** | |
| **Output** (generated SQL + optional one-line explanation) | **~160** | |

That is **2.8% output and 97.2% input**. Two consequences follow immediately:

1. **Output price is nearly irrelevant.** A model with a 8× output multiplier is barely penalised, because it writes so little.
2. **Input price and the cache discount are everything.** The 5,100 tokens of DDL and exemplars are byte-identical between requests, which is exactly the pattern prompt caching exists for.

> **Key insight**: in a text-to-SQL workload the generated query is 2.8% of the tokens, so the bill is a caching problem wearing a pricing-problem costume. Two models with the same list price can differ by 4× in real cost depending on their cache ratio.

A model with no cache discount is the wrong choice for a large, stable schema no matter how low its list price looks.

## Which model should you use for each tier?

Prices answer "what does it cost", not "what can it do". Vendors publish general reasoning and coding benchmark scores, but none of them publish text-to-SQL execution accuracy for these exact snapshots, so the tiering below is by price and reasoning class — validate it on your schema with the test in the next section before you commit.

| Tier | Job | Best value on TokenPAPA | Cached 10k queries |
|---|---|---|---:|
| **Draft** | autocomplete, schema-browsing, "show me the tables that could answer this" | Qwen 3.8 Flash, GLM-5.3-Flash | $2.21 – $3.32 |
| **Default production** | routine BI questions on a documented schema | DeepSeek V4 Flash | $4.09 |
| **Hard cases** | multi-CTE analytics, ambiguous joins, dialect corners | DeepSeek V4 Pro (budget), Claude Sonnet 5.5 / GPT-6.1 Sol (quality) | $16.71 – $30.24 |
| **Very short outputs, no cache** | classification-style "which table" routing | Claude Haiku 5.5 | $1.35 flat |

### The cheapest absolute option is not the default choice

At $0.01 input and $0.50 output per 1M tokens, **Claude Haiku 5.5** is the cheapest model on this table for a 160-token answer, and it stays at $1.35 even with a perfect cache hit — because its cached price equals its input price. That makes it excellent for a narrow job: short outputs, or schemas too small and too volatile to cache. It is a poor fit for a large stable warehouse where a cacheable 5,000-token prefix is sitting right there, and you should treat its 50:1 output multiplier as a warning if your generated SQL tends to run long.

### The escalation pipeline that actually wins

Almost nobody needs one model for every query. Split the traffic:

1. **Draft** with a cheap tier (DeepSeek V4 Flash, ~$4.09 per 10k cached).
2. **Validate** the generated SQL mechanically: parse it with the target dialect's parser, check every referenced table and column against the schema, run `EXPLAIN` on a replica, and reject anything that scans without a filter or exceeds a cost threshold.
3. **Escalate only the rejects** to a strong tier.

If 25% of queries escalate, the blended cost is **$11.65 per 10,000 queries** (0.75 × $4.09 + 0.25 × ($4.09 + $30.24)) — about **61% cheaper** than sending everything to Sonnet 5.5 at $30.24, while the queries that actually needed the strong model still get it.

> **Key insight**: a validator plus a cheap model beats a single expensive model on both cost and reliability, because parsing and `EXPLAIN` catch the failure modes that "the SQL looks plausible" never does.

## How do you measure accuracy without a leaderboard?

Public text-to-SQL benchmarks are trained on well-documented academic schemas. Your warehouse has `crm_stg_orders_v3`, three columns named `status`, and a join path nobody has written down. The only accuracy number that means anything is the one you measure.

Build a **golden set**:

1. **Collect 100–200 real questions** from analysts, support tickets and dashboards. Not invented ones — real phrasing, including the sloppy ones.
2. **Attach a known-good query** to each, written by someone who knows the schema.
3. **Run every candidate model** against the same prompt builder, temperature 0, on a read-only replica.
4. **Score by execution accuracy**, never by string comparison: run both queries and compare the result sets as multisets. Two queries that differ only in join order, aliases or `WHERE a = 1 AND b = 2` ordering are equivalent, and a string diff will mark them wrong. For ordered results, compare after stripping `ORDER BY` or compare with `EXCEPT`/`UNION ALL` in both directions depending on dialect.
5. **Break results down by difficulty** — single-table filters, one join, three-plus joins, window functions, date arithmetic. A model that is 90% on single-table and 40% on multi-join is a different purchase decision from a flat 70%.
6. **Record cost per successful query**, not cost per query. A model that is half the price but fails twice as often is more expensive per working answer.

| Metric | What it tells you | What it hides |
|---|---|---|
| Execution accuracy | Does the query answer the question | Whether the SQL is readable or safe |
| Exact-match string accuracy | Nothing useful — penalises equivalent SQL | The only thing that matters |
| Cost per 1k queries | Your invoice | Your failure rate |
| **Cost per successful query** | The number to buy on | Long-tail schema failures |

Re-run the golden set whenever you swap models, change the prompt builder, or migrate a schema. A model swap is a one-line change on an OpenAI-compatible endpoint, which makes it cheap to test and therefore tempting to do without testing.

## What does the code look like?

One key, one base URL, any of the models in the table above:

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["TOKENPAPA_API_KEY"],
    base_url="https://tokenpapa.ai/v1",
)

SYSTEM = (
    "You translate questions into {dialect} SQL. "
    "Use only the tables and columns in the schema. "
    "Return SQL only, no prose, no markdown fences."
)

def generate_sql(question: str, schema_ddl: str, exemplars: str) -> str:
    resp = client.chat.completions.create(
        model="deepseek-v4-flash",          # change this line to switch models
        temperature=0,
        max_tokens=400,                      # answers are short; cap them
        messages=[
            {"role": "system", "content": SYSTEM.format(dialect="postgres")},
            # static prefix first, so it is the part that gets cached
            {"role": "user", "content": schema_ddl},
            {"role": "assistant", "content": "Understood. I will use only this schema."},
            {"role": "user", "content": exemplars},
            {"role": "assistant", "content": "Understood. I will follow these examples."},
            {"role": "user", "content": question},
        ],
    )
    return resp.choices[0].message.content.strip()
```

Three details in that snippet matter more than the model name:

- **Static content goes first.** Prompt caching works on the longest matching prefix, so schema before exemplars before question. Interleaving a timestamp or the user's name into the system prompt destroys every cache hit you had.
- **`temperature=0`.** Text-to-SQL is not a creative task; sampling variance shows up as schema hallucinations.
- **`max_tokens` capped at 400.** Output is the expensive half on some models, and an uncapped answer that starts explaining itself costs you tokens you did not want.

Streaming is unnecessary here — a 160-token answer arrives in one pass, and streaming adds a code path you have to maintain for no UX gain.

## How do you keep generated SQL safe?

An LLM that writes SQL is an LLM with a database cursor if you let it. The controls are boring and they are not optional:

| Control | Implementation | Why |
|---|---|---|
| Read-only role | Separate DB user with `SELECT` only, no `INSERT`/`UPDATE`/`DROP`/`GRANT` | A prompt injection in a column comment should not be able to write |
| Table allowlist | Restrict the schema you send *and* the tables the role can read | Limits both hallucination and damage |
| Statement timeout | `SET statement_timeout = '5s'` on the session | A missing join predicate becomes a 5-second error, not a 5-minute outage |
| Row limit | Inject `LIMIT 1000` on generated queries that lack one | Protects memory and the replica |
| Parser check, not prefix check | Parse with the dialect parser and assert a single `SELECT` statement | `SELECT ... ; DROP ...` passes a naive `startswith` test |
| Replica | Point text-to-SQL at a read replica | Keeps reporting load off production |

The parser check is the one teams skip and the one that matters. A string that starts with `SELECT` is not a guarantee of a single read statement; a parse tree is.

## FAQ

### Which LLM is best for SQL generation in 2026?

There is no single winner, because text-to-SQL is input-dominated. For a 5,500-token prompt with a 160-token answer, DeepSeek V4 Flash costs about **$4.09 per 10,000 queries** once 95% of the schema prefix is cached, while Claude Sonnet 5.5 and GPT-6.1 Sol cost about **$30.24** for the identical workload. Start on a cheap tier and escalate only the queries that fail validation.

### Why does prompt caching matter more than price for text-to-SQL?

Because the schema DDL and few-shot examples are resent on every query and they are byte-identical. Output is only **2.8%** of the tokens, so 97% of what you pay for is repeated context. DeepSeek V4 Flash caches input at **$0.01 per 1M tokens** against a $0.30 list price, cutting a 10,000-query run from **$18.42 to $4.09** — a 78% reduction. Models whose cached price equals their input price, such as Claude Haiku 5.5, get no benefit at all.

### How do I measure text-to-SQL accuracy instead of guessing?

Build a golden set of 100–200 real analyst questions with a known-good query for each, run every candidate model on a read-only replica at temperature 0, and score by **execution accuracy** — execute both queries and compare result sets, not SQL strings. Two queries that differ only in join order or aliases are equivalent, and string matching marks them wrong. Then report cost per *successful* query, not cost per query.

### Is it safe to let an LLM write queries against a production database?

Only with a read-only role, a statement timeout, an explicit table allowlist and a row limit injected into every generated query. Never connect a text-to-SQL model with credentials that can write, drop or grant, and parse the generated SQL with a real dialect parser before execution instead of trusting a string prefix check.

### Can I switch text-to-SQL models without rewriting code?

[TokenPAPA](https://tokenpapa.ai) exposes one OpenAI-compatible endpoint at `https://tokenpapa.ai/v1`, where a single key reaches 80+ model entries, so moving from `deepseek-v4-flash` to `qwen3.8-flash` or `claude-sonnet-5-5` is a one-line `model=` change with no SDK or prompt rewrite. That is also what makes a golden-set comparison cheap enough to actually run.

### Should I use a reasoning model or a fast model for text-to-SQL?

Use a fast model for the common case and a reasoning-class model only for hard cases. Most analyst questions are single-table filters and one or two joins, where a fast tier is accurate and 3–7× cheaper. Multi-CTE analytics, ambiguous join paths and dialect-specific date arithmetic are where a stronger model earns its price — send only those, after a validator has rejected the draft.
