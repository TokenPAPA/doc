## The two errors you will hit

This is the part no pricing table tells you. GPT-6 models reject two parameters that essentially every existing OpenAI integration sends by default.

### Error 1: `max_tokens`

```json
{
  "error": {
    "message": "Unsupported parameter: 'max_tokens' is not supported with this model. Use 'max_completion_tokens' instead.",
    "type": "unsupported_parameter",
    "code": "unsupported_parameter"
  }
}
```

HTTP 400. The fix is mechanical, but it is a **hard break**, not a warning — if your client library hard-codes `max_tokens`, every call fails until you upgrade or patch it.

### Error 2: any non-default `temperature`

```json
{
  "error": {
    "message": "Unsupported value: 'temperature' does not support 0.7 with this model. Only the default (1) value is supported.",
    "type": "unsupported_value",
    "code": "unsupported_value"
  }
}
```

HTTP 400 again. The correct fix is to **delete the parameter**, not to set it to `1` — some SDKs emit `temperature` automatically when you build a config object, so check what your client actually sends on the wire.

Why this happens: these are reasoning-capable models. Sampling parameters that make sense for a single-pass completion do not map onto a model that plans internally before answering. The `usage` block confirms it — responses carry `completion_tokens_details.reasoning_tokens`, and `service_tier` is present alongside a `latency_checkpoint` object.

### Working request

```bash
TOKENPAPA_API_KEY="sk-..."

curl https://api.tokenpapa.ai/v1/chat/completions \
  --oauth2-bearer "$TOKENPAPA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-6.1-sol",
    "messages": [
      {"role": "system", "content": "You review pull requests. Reply with findings only."},
      {"role": "user", "content": "Review this diff for race conditions: ..."}
    ],
    "max_completion_tokens": 1200
  }'
```

Note what is *absent*: no `max_tokens`, no `temperature`. Adding either one puts you back at HTTP 400.

### Python

```python
from openai import OpenAI

client = OpenAI(
    api_key="sk-...",
    base_url="https://api.tokenpapa.ai/v1",
)

resp = client.chat.completions.create(
    model="gpt-6.1-sol",            # or "gpt-6-astra"
    messages=[{"role": "user", "content": "Summarise this incident report: ..."}],
    max_completion_tokens=1200,     # NOT max_tokens
    # temperature omitted on purpose - only the default is accepted
)

print(resp.choices[0].message.content)
print(resp.usage)
```

The response is standard `chat.completion`, so existing parsing code, streaming plumbing and logging keep working. What changes is the request side.

## Cost model: what the 5× actually means

Per-request arithmetic at $1.86 / $9.30 (sol) and $9.30 / $46.50 (astra):

```
sol   = (input_tokens  × 1.86 + output_tokens × 9.30)  / 1,000,000
astra = (input_tokens  × 9.30 + output_tokens × 46.50) / 1,000,000
```

A concrete shape — 8,000 input tokens and 1,500 output tokens per call, 1,000 calls/day:

| Scenario | Per call | Per day | Per month |
|---|---|---|---|
| `gpt-6-astra` | $0.1442 | $144.15 | ~$4,324 |
| `gpt-6.1-sol` | $0.0288 | $28.83 | ~$865 |
| `gpt-6.1-sol`, 80% input cached | $0.0176 | $17.57 | ~$527 |
| `gpt-5.6-sol` (for comparison) | $0.0928 | $92.80 | ~$2,784 |

Two conclusions:

1. **Migrating from `gpt-5.6-sol` to `gpt-6.1-sol` cuts this workload by ~69%** with no change in request shape. That is a rare "same workload, smaller invoice, better model" move.
2. **Cached input is where Sol gets cheap.** At $0.10 per 1M cached tokens, a stable system prompt plus a fixed document corpus drops the effective per-call cost by another 39% at 80% hit rate. Astra gets the same treatment but starts from five times higher.

## How to choose

The 5× ratio makes this simpler than most model decisions:

**Use `gpt-6.1-sol` as your default.** Chat, RAG, extraction, classification, coding assistance, summarisation, anything user-facing and synchronous. At $1.86 / $9.30 it is priced like a mid-tier model while being positioned as the flagship. For most teams this replaces both the old flagship slot *and* the mid-tier slot in one move.

**Use `gpt-6-astra` for long-horizon agent work.** Computer and browser operation, multi-step research, work where one wrong final answer costs more than five times the tokens. If a failed run means a human re-does an hour of work, $0.14 per call is not the expensive part.

**Route, do not choose once.** Both IDs share a key and a balance, so the routing table costs nothing to run:

| Workload | Model |
|---|---|
| Chat / support replies | sol |

That last row is the highest-leverage pattern. Run sol first, and on a validation failure or a self-reported low-confidence answer, retry on astra. You pay the 5× only on the minority of requests that need it.

## Migration checklist

1. **Search your codebase for `max_tokens`** and replace with `max_completion_tokens`. Grep for it — client SDKs sometimes inject it internally.
2. **Drop `temperature`, `top_p`, `presence_penalty`, `frequency_penalty`.** Only defaults are accepted; passing `1` explicitly is not the same as omitting.
3. **Keep a golden set of 20–50 real prompts** and run old vs new side by side before switching production traffic.
4. **Watch `reasoning_tokens` in `usage`.** It is billed as output. A prompt that makes the model think for 2,000 tokens costs six times what a short answer suggests.
5. **Turn on prompt caching for stable prefixes.** At $0.10 / 1M cached input the economics change materially — but only if your prompt prefix is genuinely stable.
6. **Set a per-request `max_completion_tokens` cap.** Without `max_tokens` there is no default ceiling you can rely on, and a runaway reasoning loop is billed at the output rate.

## What it does not solve

Being explicit, because "should you switch" is the only question that matters:

- **Parameter errors are not model errors.** If your integration sends `max_tokens`, GPT-6 will look broken. It is not.
- **A 5× cheaper flagship does not make a bad prompt good.** Sol is cheaper than `gpt-5.6-sol`, not cheaper than a well-designed pipeline.
- **Reasoning tokens are invisible cost.** Token counts in `usage` include thinking you never see. Budget on `total_tokens`, not on the length of the answer.
- **No self-hosting.** This is a hosted API with the usual data-handling implications for regulated workloads.
