# Which LLM Is Best for RAG in 2026? Cost per Grounded Answer

Ask ten engineers which model to use for RAG and you will get ten opinions, usually about benchmarks. But retrieval-augmented generation is not a benchmark-shaped workload. **It is a bill-shaped one.** You stuff five retrieved chunks, a citation ruleset and a question into every call, and you get back a short paragraph. In a realistic setup that is roughly 8,000 input tokens and 500 output tokens — 94% input. Which model is "best" then depends far less on which one reasons better and far more on which one prices repeated context cheapest, and whether its cache actually hits.

This guide prices 17 models on TokenPAPA for that exact workload, shows how the ranking reorders once prompt caching is on, and gives you a faithfulness test you can run on your own documents instead of trusting a leaderboard.

> **Best LLM for RAG, in one paragraph**: for most teams the best RAG model is the cheapest one that passes your citation check, because 94% of a RAG prompt is repeated context. On TokenPAPA's live prices (read 2026-11-19), at a 75% cache hit rate, Mimo V2.6 Flash costs about **$0.49 per 1,000 grounded answers**, DeepSeek V4 Flash about **$1.26**, Claude Sonnet 5.5 and GPT-6.1 Sol about **$8.97**, and Claude Fable 5.1 about **$44.54**. Run the cheap tier first, escalate only answers that fail validation.

## Why does RAG billing behave nothing like chat billing?

A chatbot call is balanced: a 400-token question, a 400-token answer. RAG is deliberately lopsided, because the whole point of retrieval is to make the model read more than it writes.

| Component of the prompt | Tokens | Repeat on every question? |
|---|---:|:---:|
| System prompt + citation rules (answer only from context, cite chunk ids, refuse if unsupported) | ~1,000 | Yes |
| Retrieved document context (5 chunks at ~1,000 tokens) | ~5,000 | Yes, in multi-turn or same-corpus chat |
| Fresh retrieval + user question + short history | ~2,000 | No |
| **Total input** | **~8,000** | |
| **Output** (answer + citation markers) | **~500** | |

That is **94.1% input, 5.9% output**. Three consequences follow, and they explain why so many RAG bills surprise people:

1. **Output multipliers matter far less than they look.** A model with an 8× output multiplier is only paying that multiplier on 6% of its tokens.
2. **Input price and the cache ratio decide everything.** Six thousand of those eight thousand tokens are byte-identical between questions — exactly the shape prompt caching was invented for.
3. **A long output budget is pure waste.** If you leave `max_tokens` at 2,000 on a grounded-answer task, you are paying for tokens the model never needed to write.

> **Key insight**: in RAG the model reads about 16 tokens for every token it writes. Any selection process that starts from output price is optimising 6% of the bill.

## What if you cannot cache the document context?

Some retrievers cannot cache. If your chunks are re-ranked per request, if you inject timestamps or user ids into the context, or if you query a different document set every time, the cache never hits and you are stuck on the cold column.

That changes the recommendation in two ways:

- **The cheap-input models win outright.** With no cache benefit, Doubao Seed 2.0 Lite ($1.03), GLM-5.3-Flash ($1.17), Qwen 3.8 Flash ($1.21) and Mimo V2.6 Flash ($1.40) all beat DeepSeek V4 Flash ($3.00) per 1,000 answers.
- **Trimming the prompt beats switching models.** Cutting retrieved context from 5,000 to 3,200 tokens — five smaller chunks instead of five large ones — removes 22% of the bill on every model at once, with no quality cost if your reranker is any good.

The caching mechanics differ per provider, so check what your route actually supports before you build a cost model on it. ## Does a cheaper model hurt answer faithfulness?

Sometimes, and it fails in specific, predictable ways rather than "being dumber". Grounded answering is an easier task than reasoning — the answer is usually sitting in the context — so the gap between a $0.003 and a $0.46 cached input model shows up in four places:

| Failure mode | What it looks like | Why cheap models fail it |
|---|---|---|
| **Context abandonment** | Model answers from parametric memory, ignoring the retrieved chunks | Weak instruction-following on long context |
| **Citation drift** | Correct answer, wrong chunk id attached | Poor span grounding |
| **Unsupported confidence** | Invents a number when the context is silent | No calibrated refusal |
| **Long-context degradation** | Quality drops past 5-6 chunks | Attention dilution |

None of these show up in a general benchmark, and all four are cheap to test. Build a gold set of 100-200 real questions, each with the correct answer and the id of the chunk that contains it, then score four numbers separately:

1. **Answer correctness** — does it match the reference answer semantically?
2. **Citation precision** — is the cited chunk actually the one with the answer?
3. **Refusal rate on unanswerable questions** — give it 20 questions whose answers are *not* in the corpus and check that it says so.
4. **Hallucination rate** — count answers containing facts absent from context.

Run every candidate on the same set at `temperature: 0`. In practice the cheapest tiers clear correctness and citation precision on single-hop questions and lose on multi-hop synthesis and on refusal — which is precisely why the routing pattern below exists. Teams that need deeper measurement methodology can borrow the execution-accuracy approach from the [text-to-SQL evaluation guide](https://doc.tokenpapa.ai/en/docs/blog/best-llm-for-sql-generation-2026); the principle is identical: compare against ground truth, not against vibes.

## How do you structure the prompt so the cache actually hits?

Caching is a prefix-matching problem. Anything that changes early in the prompt invalidates everything after it, so the order is not stylistic — it is the whole mechanism.

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["TOKENPAPA_API_KEY"],
    base_url="https://tokenpapa.ai/v1",
)

# 1. Static block: identical on every request -> cacheable prefix
SYSTEM = """You answer only from the provided context.
Rules:
- Cite the chunk id in square brackets after every claim.
- If the context does not contain the answer, reply exactly: NOT_IN_CONTEXT
- Never use outside knowledge. Never invent numbers."""

def answer(question: str, chunks: list[dict]) -> str:
    # 2. Semi-static block: retrieved context, stable order, no timestamps
    context = "\n\n".join(
        f"[{c['id']}] {c['text']}" for c in chunks
    )
    resp = client.chat.completions.create(
        model="deepseek-v4-flash",       # swap to qwen3.8-flash with no other change
        temperature=0,
        max_tokens=600,                  # grounded answers are short; do not pay for more
        messages=[
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": f"CONTEXT:\n{context}\n\nQUESTION: {question}"},
        ],
    )
    return resp.choices[0].message.content
```

Three rules make the difference between a 75% hit rate and a 0% one:

- **Never put a timestamp, request id or user name in the system prompt.** It changes the prefix on every call and you pay full price forever.
- **Keep chunk order deterministic.** Sort by score, not by dictionary iteration order, or the prefix changes between identical questions.
- **Cap `max_tokens`.** Output tokens carry a 3-8× multiplier; a 600-token cap is not a quality risk on grounded answering, it is a cost control.

## FAQ

### Which LLM is best for RAG in 2026?

There is no single best model, because a RAG call is 94% input tokens. For an 8,000-token prompt with a 500-token answer, Mimo V2.6 Flash costs about $0.49 per 1,000 answers at a 75% cache hit rate, Qwen 3.8 Flash about $0.58, DeepSeek V4 Flash about $1.26, and Claude Sonnet 5.5 or GPT-6.1 Sol about $8.97 for the same workload. Route cheap first and escalate only answers that fail your citation check.

### Why does prompt caching matter more than list price for RAG?

Because the retrieved chunks and system instructions are resent on every question and are largely identical between turns. Cacheable input is 75% of an 8,000-token RAG prompt, and the cached price ranges from $0.003 per 1M tokens on Mimo V2.6 Flash to $0.46 on GPT-5.6 Sol. Ignoring the cache ratio can make two models with the same output multiplier cost 4× apart in production.

### How do I test whether a cheap RAG model is good enough?

Build a gold set of 100-200 real questions with the correct answer and the chunk that contains it, then score four things separately: answer correctness, citation precision, refusal behaviour when the context is missing, and whether the model invented facts outside the provided context. A model can look fluent and still fail the last two, which are the ones users notice.

### Can I switch RAG models without rewriting my pipeline?

Yes. TokenPAPA exposes one OpenAI-compatible endpoint at `https://tokenpapa.ai/v1` where a single key reaches more than 60 model entries, so moving from `deepseek-v4-flash` to `qwen3.8-flash` or `claude-sonnet-5-5` is a one-line model change. Your retriever, prompt template and citation parser stay the same.

### Is a 2,000-token output budget wasteful for RAG?

It is, unless you cap it. Grounded answers with citations rarely need more than 400-600 tokens, and output tokens are billed at a 3-8× multiplier on most models. Setting `max_tokens` to 600 is the single fastest cost fix in a RAG pipeline, and it also makes latency predictable.
