# GPT Image 2.5 on TokenPAPA: flare vs sunburst — Pricing and API Guide

**GPT Image 2.5 is now listed on TokenPAPA as two model IDs — `gpt-image-2.5-flare` and `gpt-image-2.5-sunburst`. Both are billed at $4.65 per 1M input tokens and $28 per 1M output tokens, and both run through the same OpenAI-compatible image endpoint and the same API key you already use for chat.**

That is roughly 13% below the previous generation: `gpt-image-2` is listed at $5.3846 input and $32.3 output per 1M tokens. If image generation is a meaningful line item in your product, that gap is worth a migration.

This guide covers exactly what the two new IDs are, what the price difference really buys you, the endpoint they answer on, working code, and how to choose between `flare` and `sunburst` without guessing.

Beyond raw visual quality, the published capability set emphasises semantic understanding, execution of complex multi-constraint instructions, text rendering, spatial relationships and creative expression. On TokenPAPA both variants cost **$4.65 input / $28 output per 1M tokens**, are available on **every plan including the default group**, and are called via **`POST /v1/images/generations`** with your existing key.

### So what is the difference between flare and sunburst?

Honestly: **there is no published difference between them on TokenPAPA.** Same price, same plan availability, same capability description, same endpoint. They behave like two checkpoints of the same generation, which is common when a provider ships more than one release candidate of an image model.

That means the right way to pick one is empirical, not from a marketing table:

1. Write 10–20 prompts that represent *your* actual workload (product shots, UI mockups, illustrated blog headers, text-in-image layouts).
2. Render each prompt on both IDs at the same size and quality settings.
3. Score on the axis you actually ship on — text legibility, adherence to negative constraints, hands/typography, edit fidelity.
4. Keep the winner as your default and route long-tail traffic to the other.

If you only want one, start with `gpt-image-2.5-flare` — nothing about the pricing or routing suggests it is the secondary variant, and you can switch to `sunburst` with a one-string change.

Two things worth noticing beyond the headline cut:

- **The cut is almost symmetric** on input and output. Providers usually discount one side only (typically input), so a cheaper model with a disproportionate output price can cost *more* for image work, where output tokens dominate. Here both sides moved, which means the saving holds regardless of how prompt-heavy your workload is.
- **Image work is output-token dominated.** Prompts are short; the rendered image is the expensive part. A 13.3% cut on the dominant term is the number that lands on your invoice.

### A cost model you can actually apply

Because image billing here is token-metered rather than per-image, the invoice is:

```
cost = (input_tokens  × 4.65
      + output_tokens × 28.00) / 1,000,000
```

For `gpt-image-2` the same formula uses `5.3846` and `32.30`. Pull one week of real usage from your dashboard, plug both pairs in, and you get the exact monthly delta for your traffic — no per-image sticker price assumptions required, and no guessing at how many tokens a given resolution "should" cost.

## What GPT Image 2.5 is actually built for

The published capability set is where the generation-over-generation step shows up:

- **Semantic understanding** — following the *intent* of a prompt, not just its nouns, so multi-clause briefs survive without prompt surgery.
- **Complex instruction execution** — several simultaneous constraints (subject, framing, palette, style, exclusions) in one request instead of iterative re-rolls.
- **Text rendering** — the historically weakest part of image models. This is the capability that makes posters, UI mockups and social cards viable without a compositing step.
- **Spatial relationships** — where things sit relative to each other, which is what separates "a cat and a sofa" from "a cat on the left arm of a green sofa".
- **Creative expression** — stylistic range, which matters when a template can't be reused across a content calendar.

And critically for product teams: it is not generation-only. It also supports **AI-driven editing** of an existing image — instruction-based retouching, style transfer, content expansion (outpainting) and detail optimisation — which means one model ID covers both your "create" and "fix" paths.

## How to call GPT Image 2.5

Image models answer on the OpenAI-compatible image endpoint, not on `/chat/completions`. Same key, different path.

### curl

```bash
TOKENPAPA_API_KEY="sk-..."
MODEL="gpt-image-2.5-flare"

curl https://api.tokenpapa.ai/v1/images/generations \
  --oauth2-bearer "$TOKENPAPA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-image-2.5-flare",
    "prompt": "a matte-black espresso machine on a concrete counter, soft morning window light, editorial product photography, no text",
    "size": "1024x1024",
    "n": 1,
    "response_format": "url"
  }'
```

### Python (OpenAI SDK, no fork required)

```python
from openai import OpenAI

client = OpenAI(
    api_key="sk-...",
    base_url="https://api.tokenpapa.ai/v1",
)

img = client.images.generate(
    model="gpt-image-2.5-flare",   # or "gpt-image-2.5-sunburst"
    prompt="a matte-black espresso machine on a concrete counter, soft morning light, no text",
    size="1024x1024",
    n=1,
)

print(img.data[0].url)
```

### Node.js

```js
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.TOKENPAPA_API_KEY,
  baseURL: "https://api.tokenpapa.ai/v1",

```

The only change from the official SDK examples is `base_url`. No proxy shim, no vendor-specific client, no response-format translation layer.

## Migrating from gpt-image-2 or dall-e

Because the wire format is the OpenAI image schema, migration is a string change:

```diff
- "model": "gpt-image-2"
+ "model": "gpt-image-2.5-flare"
```

Nothing else in the request body has to move. Your existing retry logic, storage pipeline and moderation step continue to work, and your key does not rotate.

Two practical notes:

1. **Don't migrate blind.** Render a fixed benchmark set on the old and new ID and keep both outputs side by side for a week before you cut over — image models regress on specific prompt families more often than on aggregate quality.
2. **Route, don't replace.** If a prompt family performs better on the older checkpoint, keep it. On TokenPAPA both IDs stay available on the same key and the same billing balance, so a per-request-family routing table costs you nothing but a dict lookup.

## When GPT Image 2.5 is the wrong choice

Being useful about the limits is part of the point:

- **You need deterministic pixel output.** Any generative image model will drift. Use templates + compositing for anything that must be pixel-identical.
- **You need vector output.** This is a raster pipeline.
- **Your volume is tiny.** At low volume the 13% saving is noise; the engineering time to re-validate prompts costs more than the tokens. Migrate when image spend is a visible line item.
- **You need on-prem or air-gapped inference.** This is a hosted API.
